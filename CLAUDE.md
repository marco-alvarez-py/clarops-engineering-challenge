## Challenge Summary

This is the **Clarops Sr. Engineer Challenge** — a Spring Boot service that receives distributed events, tracks flow state by `traceId`, and reports TTL-based expiration. The two endpoints to implement are:

- `POST /api/events` — ingest an event and update trace state
- `GET /api/traces/{traceId}/status` — return current trace status

Valid trace statuses: `STARTED`, `WAITING_OTHER_EVENT`, `TTL_EXPIRED_FOR_EVENT`, `COMPLETED`.

## Commands

### Run the application

```bash
./mvnw spring-boot:run
```

Spring Boot automatically starts the Docker stack (`docker/docker-compose.yml`) via the `spring-boot-docker-compose` dependency. No separate `docker-compose up` needed. Requires `docker/.env` to exist (copy from `docker/example.env`).

### Run all tests

```bash
./mvnw test
```

### Run a single test class

```bash
./mvnw test -Dtest=TraceStatusServiceTest
```

### Format code and verify (run before committing)

```bash
./mvnw clean spotless:apply verify
```

Spotless formats Java (Google Java Format), SQL, Markdown, and `pom.xml`. It only runs during `verify` — not `package` or `test`. Always run `spotless:apply` before `verify` to avoid format-check failures.

### Run Hurl E2E tests (requires the app to be running)

```bash
hurl --test hurl/*.hurl
```

### Reset the database (re-runs init scripts)

```bash
cd docker && docker-compose down -v && docker-compose up --build
```

## Architecture

### Package structure

Base package: `com.clara.challenge`. The existing health check pattern (`HealthController` → `HealthService` → `HealthRepository` → `Health` entity) shows the expected layering: Controller → Service → Repository → Entity.

### Database

- Schema: `clarops_challenge_schema` (PostgreSQL 15, Bitnami image)
- DDL lives in `docker/init-scripts/db/01-init-schema.sql` — this is the only migration mechanism (no Flyway/Liquibase)
- `spring.jpa.hibernate.ddl-auto: none` — Hibernate never touches the schema; all DDL must be in the SQL init script
- UUIDs are generated by the application layer, not the database
- The Docker volume persists data between restarts; use `docker-compose down -v` to wipe and re-initialize

### Configuration

- Server context path is `/api` — all endpoints are under `/api/...`
- `application.yaml` connects to `localhost:5432` with credentials from the `.env` file
- Spring Docker Compose path is overridable via `DOCKER_COMPOSE_FILE` env var

### Code generation

- **Lombok** for boilerplate (`@RequiredArgsConstructor`, `@Data`, etc.) — excluded from the final JAR
- **MapStruct** for DTO-to-entity mapping — annotation processor must run before Lombok (ordering is configured in `pom.xml`)

### Testing

- JUnit 5 + Spring Boot Test are available
- Unit tests should cover state transition logic in isolation (no Spring context needed for pure business logic)
- Hurl tests go under `hurl/` and validate the public HTTP API end-to-end

## Key Implementation Decisions to Document

The challenge explicitly requires documenting these choices in `README.md`:

1. **TTL calculation basis** — `occurredAt` vs. server-received time
2. **Duplicate `eventId` handling** — reject (409) or idempotent accept
3. **Unexpected event name** — event doesn't match `nextExpectedEvent`
4. **Late event** — expected event arrives after TTL already expired
5. **Completed trace** — whether it accepts further events
6. **`metadata` storage** — JSONB column recommended for flexibility
7. **Unknown `traceId` on status query** — 404 vs. empty response
